# GitHub 원장과 독립 상태로 하루 두 편을 발행

## Decision

DIEM V2는 별도 데이터베이스 없이 GitHub의 일일 JSON 원장, 커밋,
Actions, Issues와 임시 Releases를 사용한다. 18:30 KST 실행에서 경제와
시사 주제를 함께 확정해 원장에 기록하고 경제 릴스를 발행한다. 21:00
KST 실행은 같은 원장을 읽어 시사 릴스를 발행한다.

경제·시사, 릴스·첫 댓글·대댓글은 독립된 상태와 재시도를 가진다.
이미 발행된 릴스는 댓글 실패 때문에 다시 올리지 않는다. 원본 이미지와
MP4는 Instagram 수집용 임시 Release에서 최대 72시간 뒤 삭제하고,
선정 근거·생성물·라이선스·상태·외부 ID와 해시는 Git에 영구 보관한다.

GitHub가 진실의 원본이며 Slack은 발행 완료, 최초 실패, 복구, 최종
실패와 발행 생략 같은 상태 변화만 전달한다.

## Context and constraints

현 규모에서는 별도 데이터베이스와 상시 서버가 주는 비용과 운영
복잡성이 이점보다 크다. 하루 두 차례 실행은 GitHub Actions와 작은
파일 원장으로 충분히 직렬화할 수 있다.

미디어 파일을 Git 이력에 계속 저장하면 저장소가 빠르게 커진다.
반대로 텍스트와 외부 ID만 남기면 선정과 발행 과정을 감사할 수 있고,
Instagram에는 최종 결과물이 유지된다.

Instagram 발행과 Git 커밋은 하나의 트랜잭션이 아니므로 발행 직후
상태 커밋이 실패할 가능성이 있다. 이를 완전히 제거할 수 없기 때문에
안정적인 `publication_key`, 발행 전 상태 커밋과 최근 Instagram
미디어 조정을 함께 사용한다.

## Alternatives considered

- 별도 SQL 또는 서버리스 DB: 동시성 처리는 쉬워지지만 현재 규모에서
  비용과 운영 표면이 커져 채택하지 않았다.
- 모든 이미지·MP4를 Git에 영구 저장: 완전한 원본 보관은 가능하지만
  저장소가 빠르게 비대해져 채택하지 않았다.
- GitHub Release에 미디어를 영구 보관: Git 이력은 작게 유지되지만
  장기 저장량과 정리 책임이 생겨 임시 보관만 채택했다.
- 경제와 시사를 각 실행에서 새로 선정: 21시 결과가 바뀌고 하루 편집
  기준을 재현하기 어려워 채택하지 않았다.
- 댓글 실패 시 릴스 재업로드: 중복 게시물을 만들 위험이 있어
  채택하지 않았다.
- Slack에 완성 콘텐츠 전송: GitHub와 Instagram에 이미 있는 데이터를
  중복 전달하고 운영 알림을 묻히게 하므로 채택하지 않았다.

## Revisit when

- 원장 파일 충돌이나 발행 후 상태 유실이 반복될 때
- 일일 발행량 또는 보관 기간이 Git 기반 조회 성능을 저해할 때
- 여러 운영자가 동시에 큐를 편집해야 할 때
- Instagram 원본 보존 정책만으로 과거 결과물 감사 요구를 충족하지
  못할 때
- Slack 외 다른 메신저가 주 운영 채널로 바뀔 때
