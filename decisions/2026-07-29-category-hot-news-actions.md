# 카테고리별 액션이 4시간마다 핫뉴스를 독립 발행한다

## Decision

DIEM은 `DIEM Economy`와 `DIEM Issue` 두 발행 액션을 24시간 동안 4시간마다,
KST 01·05·09·13·17·21시에 각각 실행한다. 각 액션은 자신의 분야만 새로 평가하고, 현재 인기 순위와
기사 게시 시각을 결합한 핫뉴스 기준을 통과할 때 선별·준비·Instagram
발행을 완료한다.

같은 날짜에 여러 실행을 보존하기 위해 일일 Git 원장은 현재 분야별 실행과
완료된 실행 이력을 함께 갖는 schema v3로 점진 전환한다. 기존 schema v2
원장은 계속 읽는다. 새 실행 전에 미완료 실행을 먼저 복구하며, 같은 사건은
같은 한국 날짜에 재발행하지 않는다.

## Context and constraints

기존 구조는 18:30에 두 분야를 함께 고정하고 21:00에 같은 큐를 재사용해,
장중 사이드카처럼 시간 가치가 빠르게 사라지는 뉴스를 제때 발행할 수 없었다.
또한 수동 `plan`과 `retry-all` 조합을 이해해야 실제 게시가 가능해 운영
표면이 불필요하게 컸다.

네이버 공개 인기 목록은 절대 조회수를 제공하지 않는다. 따라서 조회수를
추정하지 않고 정규화 순위, 기사 게시 후 경과 시간과 기존 편집 가치만을
검증 가능한 핫뉴스 신호로 사용한다. 별도 DB와 상시 서버는 도입하지 않는다.

## Alternatives considered

- 하루 첫 실행에서 분야별 한 건만 발행: 구조는 단순하지만 첫 게시 뒤에
  발생한 긴급 경제·시사 뉴스를 다룰 수 없어 채택하지 않았다.
- 뉴스 활동 시간대 네 차례만 실행: 해외 시장·국제 이슈처럼 새벽에 급변하는
  뉴스를 놓칠 수 있어 채택하지 않았다. 새벽에도 핫뉴스 게이트를 통과한
  경우에만 발행한다.
- 별도 큐 DB 도입: 동시성 처리는 쉬워지지만 현 규모와 0원 운영 원칙에 비해
  운영 비용과 복잡성이 커 채택하지 않았다.
- 절대 조회수 추정: 공개 근거가 없어 재현성과 신뢰성을 해치므로 채택하지
  않았다.

## Revisit when

- 하루 발행량이 과도하거나 반대로 중요한 속보 누락이 반복될 때
- 검증 가능한 실시간 조회수·공유량 API를 사용할 수 있게 될 때
- 단일 일일 원장 충돌이 반복되어 분야별 파일 분리가 더 단순해질 때
- 새벽 실행의 발행 가치보다 무료 API 소진과 피로도가 크다는 인사이트가 쌓일 때
